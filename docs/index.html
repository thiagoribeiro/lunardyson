Execution runtime for untrusted Luau

Let the model write the program.
Decide what it can touch.

A host hands LunarDyson a small program, usually written by an LLM. It runs in a sandboxed Luau VM and can reach the outside world only through the tools the host registered, each with its own budget. It is type-checked against those tools before it runs, and everything it does is metered.

One program instead of a tool loop

Agents usually orchestrate tools one model call at a time: LLM → tool → LLM → tool → …. Every step pays latency and tokens, and the path can change between runs. Asking the model for one small program and executing it deterministically is cheaper and repeatable. The catch is that you are now running code nobody reviewed. LunarDyson is built for exactly that.

Default deny

No os, io, debug, require, load*, getfenv, coroutine. A tool the host did not register does not exist in the program's environment.

Checked before it runs

ld_check type-checks the program against the registered tool signatures with Luau's analyzer, strict or nonstrict. Using a result without checking its error, or a wrong field, fails here, without running anything.

Metered, and violations stick

Memory, VM time, calls and response bytes per tool, and calls per effect class: pure, read, write, external_write, money. pcall cannot swallow a violation.

The step API

There are no callbacks across the ABI. Execution stops at every tool call and hands control back to the host, so the same loop works for sync, async and remote tools, in any language.

  1. Register tools with a Luau signature, an effect class and budgets.
  2. Check the program against those signatures (optional, recommended for generated code).
  3. Start the execution with a JSON input. It runs until it finishes, fails, or calls a tool.
  4. Resume with the tool's JSON result (or an error). Each call carries a sequential call_id, the hook for effect journaling and replay.
  5. Read the output, or a typed error kind: timeout, memory, budget, unknown tool, runtime error.
import lunardyson as ld

rt = ld.Runtime(memory_mb=16, cpu_time_ms=1000,
                max_effects={"money": 0})
rt.declare_types("type Customer = { ok: true, name: string }"
                 " | { ok: false, error: string }")
rt.tool("crm.get", crm_get,
        signature="(args: { id: string }) -> Customer",
        max_calls=20)

diagnostics = rt.check(source, strict=True)
result = rt.execute(source, {"id": "c1"})
# Result(ok, output, error_kind, message, stats)
ld_runtime* rt = ld_runtime_new(NULL);  // 16 MiB, 1000 ms
ld_tool_register(rt, "crm.get",
    "(args: { id: string }) -> Customer",
    LD_EFFECT_READ, 20, 64 * 1024);

ld_exec* ex;
ld_status st = ld_exec_start(rt, src, len, "{\"id\":\"c1\"}", NULL, &ex);
while (st == LD_PENDING_TOOL) {
    ld_call call; ld_exec_pending(ex, &call);
    // call.call_id, call.tool, call.args_json
    st = ld_exec_resume(ex, result_json, result_len);
}
// LD_DONE → ld_exec_output()   LD_ERROR → ld_exec_error()
ld_exec_free(ex);
--!strict
function run(input: Input, context: Context): Output
  local c = tools.crm.get({ id = input.id })
  if not c.ok then
    return { error = c.error }
  end
  return { greeting = "Hello, " .. c.name }
end

-- Reading c.name before checking c.ok is a type error:
-- ld_check rejects it before the program ever runs.

The program defines a global run(input, context) and returns a plain table, serialized to JSON. Go has the same shape: NewRuntime, Tool, Check, Execute, Start/Resume. The whole C ABI is 18 functions.

What it guarantees, and how that is tested

Every control has a conformance case. The same attack and contract suite runs in every binding, and the core is built and run under ASan, UBSan, LeakSanitizer and ThreadSanitizer. Two libFuzzer targets run in CI: one runs arbitrary programs with arbitrary tool replies and checks the guarantees on every step, and the other feeds arbitrary source to the type checker.

What it does not promise

  • No process isolation yet. The runtime lives in the host process; a memory-safety bug in it or in Luau would take the host down. For hostile workloads, run it in a worker process or container. A worker pool and lunardyson-server are on the roadmap.
  • Tools are the host's job. LunarDyson counts and limits calls; what a tool does (SSRF checks, authorization, idempotency) is up to the host.
  • Timing side channels are out of scope.

Why Luau, upstream and pinned

  • Gradual types let generated code be checked against tool signatures before it runs.
  • Built for sandboxing: read-only builtins, interrupts, a pluggable allocator.
  • No fork. Luau is a pinned submodule, so the language saved programs are written in does not drift. LunarDyson is the shell around it.
  • It is Luau, not Lua: Lua 5.x code will not run unchanged.

Where it runs today

RiteSmith turns intents into Trama workflows and Luau scripts. Every generated script is type-checked by LunarDyson against the tool signatures derived from RiteSmith's capability contracts, run against its test cases, and executed in LunarDyson in production with memory, time, tool and effect budgets.

Roadmap

  • Next: process isolation. The VM runs in a child process with a memory limit, and tools stay in the host, bridged by the step API. This grows into lunardyson-server
  • An async host helper built on start()/resume()
  • Only if profiling asks: a faster tool path, native codegen, a lighter GC policy
  • Done: CI on x86_64 and aarch64 with sanitizers, release wheels, continuous fuzzing

The name

Lua is Portuguese for "moon", and a Dyson sphere is a shell built around a star to capture all of its output. LunarDyson is a shell built around the moon. The moon stays untouched: Luau is used upstream, with no fork. Nothing leaves the sphere except through the shell, and the shell meters everything that crosses it. And like the moon, a LunarDyson program has no light of its own: it only works with what the host shines on it through tools.
